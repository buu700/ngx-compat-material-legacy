# R01–R03: audited engineering readiness and owner-controlled release

## R01 — Repair findings and make the final source explicit

Complete all closeout and A01–A10 scopes. Fix confirmed blockers and review their regressions; make any legitimate deviations or risk acceptance exact, independently documented and authorized where required. A label such as low severity does not excuse a required compatibility/test gap. If an owner-only approval is missing, continue independent final preparation and clearly block affected admission.

Choose library/CLI versions from the actual reviewed support design and current registry availability before the final build. Preserve the separate 22/21 library lines. Resolve whether CLI code is shared or versioned per line so one immutable package version never denotes different bytes. Inspect actual package contents, executable metadata, source maps, Sass, declarations/testing/schematics, peer/engine ranges, LICENSE/NOTICE/provenance and public documentation. Do not add a registry release merely to test version availability.

Commit final product source, tests, locks/policies, oracle/decision records and current documentation before the trusted final verification. Record exact main/21.x commits and trees. Baseline archives and working-iteration passes are not promoted by restamping metadata. A source, peer, policy, tool, oracle, fixture, relevant decision or version change invalidates dependent evidence and review; reexecute/review the affected scope.

## R02 — Run, independently validate and seal both exact artifacts

Use trusted canonical clean builds to produce one fresh identified library artifact per line and the exact identified CLI artifact(s). Keep source/lock/policy/tool/browser/oracle and build command identities. All package checks must consume those bytes; no silent repack or workspace fallback. Run the complete applicable historical, API/DI, source/packed policy, migration, Sass/companion/M3, browser/native/CSP/SSR, consumer floors, dependency/advisory and release metadata scopes.

Required negative cases remain active. Independently inspect that the accepted roster corresponds to the product contract and that reports describe real operations; do not accept 20/20 alone. Reconcile all discovered/executed/failed/skipped/N/A IDs and legitimated exceptions. A pending decision, inaccessible runtime, incomplete lookup or missing report is not pass. Requery time-sensitive advisory/eligibility inputs at finalization and recheck exception expiry; do not rely on planning-day data.

Run the existing full evaluator and sealer with the matrix digest captured from reviewed source. Verify every consulted artifact, detail/assertion, execution record and expected input is covered and rehashed across the finalization boundary. Check moved archives and reject tampering, wrong-line swaps, stale reports, missing cases and false assertion subjects. Keep one final immutable index joining the two independent line manifests; do not merge their successes into an invented single run. The audit coverage record must bind the final source/content and acknowledge any explicitly unchanged reviewed files.

Retain exact artifacts, full reports, raw browser traces/screenshots where relied upon, reproducing commands, run/attempt provenance and integrity indexes in durable authorized storage. Link ephemeral Actions artifacts only with a retention plan and preserved exact bytes. No secrets/private Cyph data in public evidence. The final manifest hash is external, not circular. A verification receipt commit afterward is not the source that was tested before it existed.

## R03 — Complete report and owner handoff

The final report includes: both source/tree/package/CLI identities; a G01–G13 table with real scope/evidence; full file/contract audit coverage and any exclusion/inheritance method; findings and repair/review history; reviewed exceptions and original authority; all commands/exits/runtime configurations; archive hashes/retrieval; known limitations and owner prerequisites. State whether the result is engineering-ready, audited-but-blocked, or still implementation/audit-incomplete. Do not say the audit is complete while a required domain was merely sampled or unread.

An engineering-ready result requires all applicable gates and mandatory decisions, no unresolved release-relevant security/compatibility/evidence gap, and final fresh complete two-line proof. In the blocked case identify exactly what is missing, its source and who/what can resolve it. Do not hide an unexecuted positive floor behind a passing range test, or an unverified grant behind a long authority string.

### Publication is a separate authorized operation

Prepare but do not execute registry publication without the owner's explicit package/version/tag/source/artifact authorization. Recheck registry ownership/authentication, actual tool support and version/tag availability. The retained project plan uses `next` for main RC and `lts-21-next` for 21.x RC; confirm the intended actual tags before publishing. Never accidentally move stable tags. Publish the accepted bytes, fetch the registry artifacts back, compare integrity/metadata and rerun independent install/consumer smoke. Upload success alone is not registry verification. A metadata/version change requiring repack requires fresh evidence.

After a partial publication failure, inspect registry state before retrying. Do not unpublish, overwrite an immutable version or move tags without authority. Provide the accepted release set and rollback/repair instructions to the authorized operator rather than using unavailable credentials as a reason to stop engineering.

### Cyph qualification is separate from the public-library audit

The owner intends production use in Cyph. The full public-library audit and compatibility lab do not themselves certify that private application. With separate application access/authority, inspect Cyph's actual framework line, dependency age policy, import/theme/provider inventory, build/tests and critical UI flows. An exact first-party RC admission under its policy requires its own owner decision; do not broaden a namespace exemption or call an ordinary release a security emergency.

Rehearse the exact registry package in a disposable/staging application, preserving unrelated animation providers and theme contracts. Test relevant overlays, forms, keyboard/focus, geometry, styling and application-specific integration. Prepare a concrete prior artifact/lock/deployment rollback and agreed observation/stop conditions before any authorized production rollout. No application access means private qualification is unperformed, not successful. A production RC decision and future stable/maintenance tranche remain explicit owner milestones.

### Future maintenance boundary

The current Chainman/CI/security architecture is audited and any current reliability defect fixed. Generalized dependency updating, Chainman self-update qualification, canaries/outreach and unrelated maintainer-platform expansion are a subsequent tranche. List appropriate follow-ups without making unrequested feature work part of this RC or weakening immediate requirements.
